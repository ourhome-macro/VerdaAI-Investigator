# 矩阵调用链与并发控制（2026-09-26）

## 调用链与 5×6 量化

`run_pipeline` 先通过 `_plan_research` 拆出最多 6 个品牌和用户指定维度，`build_contract` 去重为品牌×维度矩阵。采集阶段每品牌执行 `_collect_brand`：按维度顺序调用 `multi_search → search → search_bocha → httpx`，随后逐页抓取正文。分析阶段 `_analyze` 对每个单元调用 `_analyze_brand`，通常一次 DeepSeek 提取、在有 Claim 时再一次 DeepSeek 原文核验。质检可触发补采与重新分析。写作阶段 `section_plan` 产生摘要＋6 维度＋结论共 8 章，指定视角多 1 章，逐章调用 DeepSeek。

| 阶段 | 旧行为与峰值 | 新默认上限 |
|---|---:|---:|
| 采集 | 单任务 2 品牌并行，每品牌搜索串行；跨任务可叠加 | 单任务 2；博查同供应商 2 in-flight / 2 RPS |
| 30 单元分析 | 30 个 Future 一次提交，3 线程实际并行；每个单元最多 2 次模型调用 | 每批只提交 3 个，DeepSeek 同供应商 3 in-flight / 2 RPS |
| 章节写作 | 一次提交 8–9 章，单任务可有 8–9 路模型请求 | 每批 3 章，DeepSeek 同供应商 3 in-flight / 2 RPS |
| 所有出站 | 无跨供应商总预算 | 同进程合计 6 in-flight / 4 RPS |

以功能、定价、口碑、生态、架构、画像这 6 维且都有官网域名、时效不是 `noLimit`、缓存未命中为例，每品牌最多 4 个官网维度×2 查询＋口碑 6 查询＋画像 1 查询＝15 次博查搜索，5 品牌首轮最多 **75 次**。不限时效时口碑少 2 次基线查询，约 **65 次**。Deep 模式最多 1 次返工，Expert 最多 2 次；若全部 30 单元都补采且缓存无效，Expert 最多约 **225 次逻辑搜索**，每次搜索最多 3 次物理尝试。实际请求会受来源档案、缓存、证据缺口、质量判定及页面可用性影响。官方页面抓取另有网络流量，不计入博查次数。

首轮 30 单元最多 **60 次逻辑模型调用**（提取＋核验）；旧版每次 `chat` 有 5 次显式 429 尝试，SDK 又可每次重试 1 次，极端情况下可放大至 **10 次物理请求/逻辑调用**。新版本关闭 SDK 隐式重试，最多 3 次物理请求/逻辑调用；非瞬态 4xx 不重试。原来多任务并跑时章节 8–9 路/任务与单元分析 3 路/任务会叠加，访客使用不同 Key 时旧博查限流器也不会共享供应商配额，429 与排队超时风险较高。

按默认 2 RPS，75 次博查搜索仅发起请求的理论下界约 37 秒；60 次模型请求仅发起请求的下界约 30 秒，两阶段还有网络响应、抓取和处理耗时。若所有博查请求都用满 3 次尝试，仅首轮就可能有 225 次物理请求，发起请求的下界约 112 秒。令牌桶允许不超过配置容量的短时突发，因此这些是容量估算，并非端到端耗时承诺。

## 实现和配置

`outbound_limit` 在一次原子准入中检查三层预算：单凭据、同供应商（跨 Key）和同服务进程全局。排队期间不占并发槽，发出请求时才消耗令牌；超出队列等待时间直接抛错。429 对该凭据设置冷却，避免同一 Key 立即重试。DeepSeek 普通和流式请求均持有许可直至响应完成；流式响应已发出内容后不重试，避免重复片段。博查对 429、408、5xx、连接失败和超时做最多 3 次指数退避，遵守数值型 `Retry-After`，加入 0–0.5 秒抖动。模型请求对 408、429、5xx、连接失败和超时同样重试。两者排队、失败、退避和完成记录到 `uvicorn.error`，日志仅包含供应商、耗时、尝试次数、异常类型和状态码，不记录 Key、提示词或查询内容。

以下变量在 `backend/.env.example` 和 `api/.env.example` 给出默认值：

| 变量 | 默认值 | 含义 |
|---|---:|---|
| `OUTBOUND_GLOBAL_REQUESTS_PER_SECOND` / `OUTBOUND_GLOBAL_MAX_IN_FLIGHT` | 4 / 6 | 同进程所有受控出站请求总预算 |
| `LLM_REQUESTS_PER_SECOND` / `LLM_MAX_IN_FLIGHT` | 2 / 3 | 同模型供应商合计预算；单 Key 也受相同上限 |
| `BOCHA_REQUESTS_PER_SECOND` / `SEARCH_MAX_IN_FLIGHT` | 2 / 2 | 博查同供应商合计预算；单 Key 也受相同上限 |
| `LLM_MAX_QUEUE_WAIT` / `SEARCH_MAX_QUEUE_WAIT` | 90s / 60s | 准入排队上限 |
| `LLM_TIMEOUT` / `SEARCH_TIMEOUT` | 180s / 30s | SDK/HTTP 的单次请求超时设置 |
| `LLM_ATTEMPTS` / `SEARCH_ATTEMPTS` | 3 / 3 | 含首次的最大物理尝试次数 |
| `LLM_RETRY_BASE_SECONDS` / `SEARCH_RETRY_BASE_SECONDS` | 1s / 1s | 退避基数 |
| `LLM_RETRY_MAX_SECONDS` / `SEARCH_RETRY_MAX_SECONDS` | 20s / 20s | 单次退避封顶 |
| `ANALYZE_BATCH_SIZE` / `WRITE_BATCH_SIZE` | 3 / 3 | 每批提交的分析单元和章节数 |

`LLM_MAX_RETRIES` 保留兼容旧环境文件，但 SDK 重试固定关闭，以 `LLM_ATTEMPTS` 为准。超时、排队和退避均可能累积，调整时应连同任务执行时限及上游配额考虑。日志可关注 `outbound_queue_timeout`、`outbound_retry`、`outbound_failed`、`outbound_complete` 中的 `queue_ms` 和 `elapsed_ms`；持续排队超时意味着配额不足或任务进入速度过高。

## 部署边界和验证

限流状态在**单个 Python 进程内**共享。当前 Docker 镜像固定 `uvicorn --workers 1`，因此覆盖该部署中所有同时运行的任务与访客 Key。Vercel 多实例/多进程不共享内存；若将该入口扩容，必须用 Redis 等集中式原子计数器替代进程内状态，并以各实例总和核对供应商额度，不能把上述数字误当成跨实例硬上限。

使用 `backend/.venv` 执行 `python -m unittest discover -s tests -p 'test_*.py' -q`，106 项通过。新增测试覆盖令牌桶速率、不同 Key 的供应商配额、跨供应商总配额、队列超时、DeepSeek 瞬态与非瞬态重试、429 的 `Retry-After`、流式输出后的失败不重放、博查 429/读取超时重试和 5×6 分批调度。测试无真实外部请求。
