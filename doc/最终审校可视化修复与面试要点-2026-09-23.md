# 最终审校可视化修复与面试要点

## 本次修复

之前最终审校会无条件清空报告的 `charts`、`structured`、`sentiment` 及章节图表。直接保留旧数据也不安全：当前主流水线只产出逐品牌、逐维度的已核验论点，旧的能力评分、市场份额估计和舆情比例没有逐值核验依据。

现在由 `backend/app/core/audited_artifacts.py` 从 `verification.verdict == supported` 且来源记录完整的论点生成：

- **覆盖图**：按品牌与维度统计已核验论点数；图表携带实际参与统计的 `claim_ids` 和 `evidence_ids`。图表表示证据覆盖，不表示产品能力评分。
- **结构化事实**：把论点 ID、品牌、维度、原文和来源链接组织成可回查的章节卡片。
- **社区观点**：仅展示来源归类为社区、且论点已核验的逐条观点和原始链接；不从少量样本推算全网情感占比。

最终审校继续过滤未经核验的正文，并用上述数据替代旧探索性可视化。读取历史已审校报告时，如果缺少新版产物，可从已保存的论点与证据即时重建；没有合格论点的报告保持空视图。`backend/` 和 Vercel 镜像 `api/` 已同步。

## 验证

- 后端单元测试：79 项通过，新增测试覆盖已核验/未核验论点混合时的图表、结构化事实、社区观点筛选，以及历史报告读取时的重建。
- 前端 `npm run build` 与 `npm run lint` 通过。构建仍提示首包体积较大，这是独立的性能优化事项。
- 用仓库中 `doc/通用矩阵-auto-报告.json` 做离线投影：12 条原论点中 10 条符合来源条件，生成 1 张覆盖图、10 条结构化事实。该样本没有合格社区观点，因此舆情面板保持空白。
- 本次未调用外部模型或搜索服务，没有宣称线上报告全流程验收。

## 面试中值得讲的亮点

1. **证据链与双维度可信度**：搜索结果并不直接成为结论；系统保留原文、来源、时间、转载归属，再核验论点支持关系。事实可信度与独立交叉验证分开表示，可解释“官方单源可信，但不是多源验证”。
2. **按研究合同驱动的多领域调研**：先把用户需求拆成品牌、维度、来源类型和时间窗口，再按格子采集与分析；缺口会触发定向返工，而不是降低通过标准。
3. **断线可回放的长任务**：后台任务与 SSE 订阅解耦；事件写入 SQLite，浏览器断线后按序号续看，SQLite 租约限制并发并标识中断。
4. **可审计的最终交付**：正文、结构化事实和图表都落到可回查的论点与证据上；模型输出未通过核验时不以确定性结论发布。
5. **工程化交付**：React/Zustand 前端、FastAPI 后端、Docker Compose 单 worker 持久化部署，另有前后端构建和单元回归。

## 面试中更有价值的难点与取舍

- **LLM 会“带着引用编事实”**：仅检查存在 `evidence_id` 不够；需检查引用片段、数字、适用范围、时间和原始来源。此次修复也遵循同一原则：图表携带来源 ID 仍不能证明图表的每个数值，所以改为由已核验论点直接计算覆盖数。
- **少量社区样本不能代表全网舆情**：原系统有情感分类与聚类组件，但当前主流水线没有具代表性的样本台账。逐条观点可以发布，百分比暂不发布。这是可信交付优先于界面丰满的具体取舍。
- **SSE 断线与进程故障是两类问题**：断线可回放，进程故障仍需重试。当前是单机 SQLite + 单 worker 架构，不应称为分布式高可用任务系统。
- **Vercel 镜像并非完整生产部署**：临时文件系统和进程内任务不适合可靠长任务；生产应使用常驻 worker 与持久数据库，或迁移到队列架构。
- **48 位专家是角色画像，不是 48 个独立 Agent 进程**：可描述为“多角色视角驱动的调研编排”，不要夸大为自治集群。

## 可用于面试的项目表述

> 我做的是一个证据可追溯的竞品调研系统。用户提出品牌与关注维度后，后端按来源和时间窗口采集网页证据，生成原子论点，再核验原文支持、来源可信度与独立验证程度。质检会对缺口定向返工，最终审校把不被论点支持的正文剔除。任务执行和 SSE 订阅解耦，事件落 SQLite 支持断线回放。我还修复了最终审校把所有图表清空的问题：图表现在统计已核验论点的覆盖数，每个结构化事实都能回查来源；没有可信样本的舆情百分比仍不展示。

被问到“最难的 bug”时，建议展开**最终审校与可视化的冲突**：直接恢复旧图表会重新引入虚构评分；正确方案是定义可验证的数据口径，再从审校后的论点重建展示，而不是只删除清空语句。
