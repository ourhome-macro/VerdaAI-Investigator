# API 限流落地方案

日期：2026-09-24

## 决策

在所有上游请求的共同入口做配额调度，而不是在矩阵编排处限制任务数。调度器同时控制 **在飞请求数**、**时间窗口内请求数** 和 **时间窗口内 Token 预算**。任务级并发仍由现有 `task_runtime.py` 控制；矩阵线程池的 3 个 worker 是计算阶段的局部上限，不是 API 配额。

当前 Docker Compose 只有 1 个后端实例，可先使用进程内共享调度器落地。但生产演进为多 worker、多实例或 serverless 时，应将配额状态和租约迁移到 Redis 等共享原子存储；SQLite 任务锁或各进程独立的 `Semaphore` 不能保证跨实例配额。

## 接入位置

| 位置 | 改动 |
|---|---|
| `backend/app/core/llm.py:116` 的 `chat()` | 每次实际发送请求前获取对应模型的配额与并发许可；请求完成或失败时释放在飞许可，记录真实 `usage`；仅 429/可重试的 5xx 进入统一重试。关闭 OpenAI SDK 自带重试，避免与业务层双重重试。 |
| `backend/app/core/search.py:73` 的 `search_bocha()` | 每次 POST 前获取博查许可；保留 HTTP 状态、`Retry-After`、响应业务码和 `log_id`；429 使用统一退避与短时冷却。 |
| `backend/app/core/search.py:166` 的 `multi_search()` | 将限流、超时与服务不可用保留为可识别的采集失败；不要把全部查询失败转化为空结果。真正无匹配结果才返回空列表。 |
| `backend/app/core/orchestrator.py:939` 的章节写作 | 将章节并发设成显式、可配置上限，并让每章的 LLM 请求仍经过公共调度器；优先保证不同任务公平，避免单任务占满全部槽位。 |
| `api/app/core/` 镜像 | 与 `backend/app/core/` 保持同一实现和测试，避免部署路径的行为分叉。 |

## 限流键与安全

- 平台共用 Key：按 `provider + account_id + model` 管理 DeepSeek 模型并发；博查按 `provider + account_id` 管理搜索速率。
- 访客自带 Key：在内存中以 `HMAC-SHA256(server_secret, provider + raw_key)` 作为配额键，不保存或记录原始 Key；各访客 Key 独立计数。DeepSeek 官方按**账号**而不是 Key 计算并发，如果同一 DeepSeek 账号提供了多个 Key，仅凭 Key 无法精确合并账户配额；还需平台总阀门和上游 429 自适应冷却，或由接入方提供可验证的账号身份。
- 计数维度按实际服务端规则配置。不要把 DeepSeek 的公开并发上限误作已知 TPM/RPM，也不要把博查平台总吞吐误作个人 Key 的 QPS。

## 一次调用的状态机

1. 生成请求预算：输入 Token 估算 + 输出 Token 上限；博查为 1 次搜索。设置任务截止时间和最大排队时间。
2. 加入按任务 ID 公平调度的有界队列；在发送前同时取得并发槽、请求窗口额度和 Token 窗口额度。等待队列时不应占用并发槽。窗口额度一旦发送即消耗，失败也不返还；在飞槽在响应结束后释放。
3. 成功后用上游 `usage` 修正 Token 计量；把估算误差留出安全余量。若实际用量大于预留，应借记后续窗口，不能把余额变成负数后继续放行。
4. 429：若有合法 `Retry-After` 则遵守；否则指数退避加随机抖动，设置同一配额键的短时冷却，再重新申请窗口额度。并发槽在等待期间释放。达到次数或截止时间则明确失败，不把失败当成无结果。5xx 按较短的独立策略重试；401/402/403 等永久错误立即失败。
5. 排队超时或队列满时，保留任务的可恢复失败状态，SSE 告知“上游繁忙／配额不足”，不要静默完成一份缺证据的报告。

## 参数与上线

- `DEEPSEEK_CORE_MAX_IN_FLIGHT`、`DEEPSEEK_AUX_MAX_IN_FLIGHT`、`DEEPSEEK_REQUESTS_PER_MINUTE`、`DEEPSEEK_TOKENS_PER_MINUTE`、`BOCHA_MAX_IN_FLIGHT`、`BOCHA_REQUESTS_PER_SECOND`、`RATE_LIMIT_MAX_QUEUE_WAIT_SECONDS` 等均设为可配置。模型相同的 `core/aux` 配置必须汇总到同一实际模型桶，不因用途标签拆成两个独立额度。
- DeepSeek 当前公开并发上限为 `deepseek-v4-pro` 500、`deepseek-flash` 2500，实际应用阈值应留给站内其他流量。官方错误码仍注明 429 可由 TPM/RPM 引发，但未在公开限速页提供固定可用数值；先核实账号额度，再配置对应窗口。博查 QPS/RPM 同样以账号控制台或官方确认为准。**不要将试运行阈值写成官方配额。**
- 先做不拦截的观测：每个提供商/模型/凭据哈希的请求数、输入输出 Token、在飞数、队列等待、429、重试、采集失败和任务完成时长。再启用保守阈值，使用 5×6 矩阵、两任务同跑和注入 429 的离线测试验证；最后逐步提高阈值。
- 验收重点：无上游 429 时不会不必要地丢失查询；429 后按等待时间重试且不会同一时刻集体重试；共享 Key 的两任务总流量不越过本地阈值；搜索限流在报告中被标为采集失败；日志和指标不包含 API Key。
