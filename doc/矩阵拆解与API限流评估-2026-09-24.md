# 矩阵拆解与 API 限流评估

日期：2026-09-24

## 结论

5 竞品 × 6 维度会产生最多 30 个原子分析任务，但当前单个调研任务不会同时发出 30 个分析请求。采集按品牌、维度和查询逐条执行；原子分析线程池最多同时运行 3 个单元。任务运行器最多容纳 2 个调研任务，且同一访客最多 1 个，因此共享账号下分析阶段最多约 6 个并行单元。每个有证据的分析单元先调用核心模型抽取事实，再调用辅助模型核验事实，两次调用通常顺序执行；无证据单元不调用模型。

这不等于已经具备生产级限流保护。章节写作会为全部章节创建并发任务；多个用户任务会叠加。项目没有按模型账号或博查 Key 统一限流的调度器，也没有请求速率和 Token 预算预留。DeepSeek 的 429 会在单次调用中退避重试，但并发任务可能一起重试。博查 429 没有退避重试，`multi_search` 会将单条搜索失败记录为 Trace 后继续，可能造成证据缺口，不能作为正常“无结果”处理。

## 外部限制的核实范围

DeepSeek 当前官方文档列出的账号级同时在飞请求上限为 `deepseek-flash` 2500、`deepseek-v4-pro` 500；同一账号的不同 API Key 合并计算。官方错误码页同时说明 429 也可能由 TPM/RPM 达上限引发，但没有在该页面给出可直接用于计算的固定 TPM/RPM 数字。因此，不能仅凭“3 个并行”保证不触发 429；需要按实际账号额度、模型、Token 大小与其他调用流量测量。

博查公开可查的资料确认 429 表示请求频率超限，但未找到可核实的当前账户级固定 QPS/RPM 配额。平台整体吞吐能力数字不能当成单个 Key 的配额。应以账号控制台、合同或官方支持给出的配额为准。

## 生产方案

1. 在所有 DeepSeek/博查出站请求的共同入口，按实际计费和限流主体建队列：DeepSeek 以账号和模型为键，博查以账号或 Key 为键。并发阀门、滑动窗口 RPM/QPS 和 Token 预算需分别控制；单机多进程时使用共享存储协调，而非每个进程各自计数。
2. 从实际配额的保守比例起步，通过 429 比例、队列等待时间和端到端完成时间调整。若官方未提供博查数字，先向平台确认，再做小流量压测；不要把示例阈值当成官方上限。
3. 429 读取 `Retry-After`（如果提供），否则指数退避加随机抖动；同一 Key 的请求共享短时冷却。设置最大重试次数与任务截止时间，避免同时重试再次冲垮服务。
4. 将博查限流与真正的零搜索结果区分开：限流时保留待重试状态或明确标注采集失败，避免后续矩阵把缺口误当成事实空白。
5. 优先复用同一品牌的搜索结果和网页正文，按维度归档证据；缓存命中可减少请求总数和费用，但不能代替限流器。

粗略估算：无缓存时，5×6 至少需要约 30 次基础搜索，官方站点与社区等补充查询还会增加数量；有证据的 30 个单元通常最多引出约 30 次事实抽取和约 30 次核验调用，返工与写作另算。这是请求总量，不是同一时刻的并发量。
